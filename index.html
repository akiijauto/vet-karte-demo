動物病院向け 電子カルテ・売上管理システム

開発中のプロトタイプ — 画面モックと、設計判断の記録

これは設計を画面に起こしたモックで、動くシステムではありません。 動くのはページ間のリンクだけで、入力・保存・検索はできません。 表示しているデータはすべて架空で、実在する動物病院・飼い主・動物の情報は含みません。外部への通信もありません。

解こうとしている問題：受付・会計（クラウドソフト）／支払い（外部レジ）／診察カルテ（紙）に 業務が3つに分断されている。同じ患者の情報が3か所に散り、突き合わせが人手になっている。

これを 飼い主 → ペット → 診察 の1軸に統合する。 ただし外部レジは現行のまま残す——請求の算出・支払い状況の記録・売上集計までを引き受け、 決済そのものは触らない。動いているものを止めないための線引きです。

外来受付から見る 診察カルテ 検査 会計 入院 顧客 予約 売上集計

画面の構成

受付から会計までを4つの画面にまとめ、タブで移動する構成にしています。 診察の途中で何度も画面を行き来するため、階層をたどらせない作りにしました。

画面役割
外来受付その日に来ている患者を一望する。ここが1日の起点になる
顧客飼い主と動物の情報。1人の飼い主に複数の動物がぶら下がる
診察カルテ稟告・現症・処置の記録。紙カルテと同じ書式で印刷できる
検査検査値と基準値。範囲を外れた項目が必ず目に入る形にする
会計その日の診療内容から請求を組み立てる
入院在院中の経過。誰がいつ何をしたかが必ず残る
予約担当と処置室の両方で埋まり具合を見る
売上集計会計の明細から積み上げる。集計を別に持たない

画面の中で使う言葉は、現場が日々口にしているものをそのまま項目名にしています—— 稟告・現症・転帰・オーナー目的。分かりやすく言い換えると、 口頭でのやり取りが通じなくなる損のほうが大きいと判断しました。

業務から出てきた設計判断

項目名を言い換えない

「稟告 → 主訴」のような置き換えは法的な効果がほとんど無く、 現場の口頭伝達が通じなくなる損だけが残ります。分かりやすさより、通じることを取りました。

同時に開けるのは1患者ぶんのタブだけ

複数の患者を同時に開けると、取り違えて別の動物のカルテに記入する事故が起きます。 便利さより、起きてはいけないことを起こさせない側に倒しました。

押せない機能は消さずにグレーで残す

消してしまうと「無い」のか「まだ作っていない」のかが区別できません。 毎日同じ位置を押している人にとっては、並びが変わること自体が負担になります。モックでも同じ扱いにしています。

カルテは常に印刷できることが前提

過去の紙運用と履歴を合わせるため、すべての診察記録が、いつでも紙と同じ書式で刷れること。 回線が切れた日に紙へ退避する手段にもなります。印刷できないカルテがあってはならないという要件です。

カルテのデータは消さない

論理削除のみ、修正は履歴を残します。診療記録は後から「無かったこと」にできてはいけないためです。

診察中は片手が塞がり、中断され、時間がない

モーダルダイアログ・保存時の確認ダイアログ・マウス必須の操作・多段階ウィザードは採りません。 使う場面の制約から、採らない選択肢を先に決めています。

音声入力は、アプリに作らない

口述入力は Windows 標準の音声入力（Win+H）を使い、アプリ側に音声機能は作りません。 こちらが作るのは「音声入力を邪魔しない画面」です——自由記述欄を大きく、キーボードだけで欄を移動でき、 入力中に画面を再描画しない。自前で持たなくてよい機能を持たない判断です。

AIに作らせるうえで、品質をどう担保したか

主眼は実装ではなく、「AIの生成物が業務要件を満たすかを、どう検証させるか」という指示設計に置いています。 受付から会計までの各段階で「何が満たされていれば正しいか」を先に定義し、AIに自己検証させたうえで人が確認する手順にしました。 金額の算定・計上に関わる箇所は、AIの出力をそのまま採用せず検算が通ることを採用条件としています。

以下は、その検証で実際に検出した不具合です。どれも「動くかどうか」を見ているだけでは見つかりません。

① 全患者のカルテに、同じ体温が印字されていた

症状
画面では正しい体温が出ているのに、印刷したカルテはどの患者も同じ値だった。
原因
印刷用の処理に、写し漏れた固定値が残っていた。
見逃した理由
印刷のチェックが「用紙からはみ出していないか」しか見ていなかったため。値が正しいかは対象外だった。
対処
固定値が存在しないことを、全患者 × 画面／印刷の252ページについて自動で検証する項目を追加した。

→ 該当するカルテ画面を見る

② 合計額が、単価未設定の行を 0 円として集計していた

症状
単価が入っていない明細行が0円として黙って足され、合計だけが正しく見えていた。
危険さ
請求額が過少になるうえ、画面上はどこも赤くならない。気づく手がかりが無い。
対処
合計を伏せる（エラーにする）のではなく、未算入の行数を明示する仕様に是正した。 業務を止めずに、異常だけが見えるようにするため。

→ 該当する会計画面を見る

③ 確定を取り消して直すと、入金の記録が2重に作られるところだった

症状
確定した伝票を当日中に取り消して直し、もう一度確定すると、入金の記録がもう1件増える。
危険さ
売上集計の未収金帳票は同じ伝票への入金を合計する作りだったため、 記録が2件あると受け取った金額が実際より多く見えてしまう。
対処
確定のやり直しでは新しい記録を作らず、既存の記録を書き直す形にした。 「もう一度確定する」と「もう一度受け取る」は違う、という区別。

→ 該当する会計画面を見る

④ 伝票を再確定すると、伝票番号が飛ぶところだった

症状
確定を取り消して直し、もう一度確定すると新しい番号が振られ、最初の番号が誰にも使われないまま欠番になる。
見逃した理由
「保留の伝票には番号を振らない」という既存の見張りはあったが、 逆向き（確定した番号を、取り消しただけでは失わない）は見張っていなかった。
対処
確定の処理を「すでに番号があれば振り直さない」形にし、同じ番号のまま保留へ戻って直し、再確定できるようにした。

要件を確定させてから実装に入る

仕様の曖昧さは、そのまま不具合になります。例：設計書が特定のライブラリを前提にしていたのに、 本体には導入されていないと判明したことがありました。動作に支障は無く、その時点の挙動も正常だったため、 独断で実装せず、方針決定を依頼して記録に残しました。

進め方

Phase 0（現状調査）→ 1 カルテコア → 2 会計・売上 → 3 予約 → 4 画像リンク → 5 AIによるカルテ下書き、 という順で進めています。受付からカルテ、会計までの1本の流れを先に通し切るのを最優先にしました。 途中で止まる業務システムは、部分的に便利でも現場では使われないためです。 Phase 1〜3 は一通り動く状態まで進み、Phase 4（画像リンク）は登録・参照まで、 Phase 5（AI下書き）は外部AIへの送信経路まで、それぞれ着手しています。

製品化するかは保留していますが、後戻りを防ぐため全テーブルに clinic_id を持たせてあります。 あとから多施設に対応しようとすると、テーブル定義とデータの両方をやり直すことになるためです。

画像（CT）はカルテに格納せず、保管先へのリンクだけを持ちます。 1検査で1,000〜3,000枚になるため、抱え込むと保存も表示も破綻します。

AIによるカルテ下書きは、特定のAIベンダーに固定していません。 呼び出し先を差し替えられる形にしてあり、キー（連携情報）を設定しない限りは動きません。 これは音声機能ではなく——診察中の口述入力は引き続き Windows 標準の音声入力を使い、 ここが受け取るのはすでに文字になった文章だけです。下書きは確定カルテに直接書き込まれず、 必ず人が読んで判断してから通常の入力欄に書き写します。
